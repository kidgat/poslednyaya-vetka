## 1. ST-001 C — окончательный план осмотров

Правило: участки осмотров **не пересекаются** с проходами, дверными проёмами, генератором,
лутингом и с **полной** зоной разговора каждого NPC (крайние точки маршрута ± radius).
Это правило добавляется в валидатор как тест, чтобы порядок «первое совпадение» не прятал
ни разговор, ни осмотр.

## 2. ST-002 — окончательная техническая схема

### Сцены (рекомендация остаётся в силе)

Отдельные сцены со своими границами, дорожками, камерой, слоями, светом и точками входа.
Станция становится сценой `station` **без изменения геометрии**.

| Сцена | Дорожки | Особенности |
|---|---|---|
| `station` | 5 нынешних этажей | без изменений; Пост 1 и тоннель к «Московской» закрыты |
| `yards` | улица/дворы (продолжение нынешней поверхности) | вход — центральный шлюз; без прохожих |
| `universam` | надземный зал · U−1 · U−2 | лестницы как служебные проходы; дверь A (склад) |
| `duplet` | торговый зал (+ проём в мастерскую) | продавец; Дед выходит по сцене |
| `service-tunnel` | одна дорожка | дверь B со стороны тоннеля |
| `peregon-west` | одна дорожка | Пост 1 снаружи; событие возвращения |

### Двери комплекса и карта Деда

- Дверь **A** — вход в подземный комплекс со стороны «Универсама-3».
- Дверь **B** — со стороны служебного тоннеля.
- Обе открываются **одной и той же** картой Деда.
- Тип карты (магнитная или перфокарта) — только оформление. Для логики это предмет
  `deda-card`; никаких систем питания и электронного доступа не вводится.
- Карта **не открывает** гермоворота станции. Это закреплено в данных: у ворот нет условия
  «нужна карта».

### Переходы между сценами («порталы»)

```
{ id, from:{scene,floor,x}, to:{scene,floor,x}, requires:[условия], dir, anim }
```

- Условия — проверка флагов, сюжетных предметов и экипировки (`requiresGasMask`, см. § 4).
- Переход идёт по образцу нынешнего служебного прохода: пока идёт анимация, ввод
  игнорируется.
- Новое положение записывается **одной** записью сохранения в момент фиксации (§ 9).

### Возвращение через Пост 1 — утверждённый эпизод как конечный автомат

```
idle → knock → recognized → passing → closed (post1ReturnDone)
```

1. На перегоне у ворот появляется действие «Постучать». Оно доступно, только если
   стадия задания разрешает событие (`stage ≥ peregonReached`).
   Стадию ставит выход из служебного тоннеля на перегон.
2. Начинается сцена: охрана узнаёт Глеба и пропускает его. Ввод заблокирован.
3. **Точка фиксации:** одной записью сохраняются `post1ReturnDone = true`, сцена `station`
   и позиция «платформа, x≈200».
4. Ворота закрываются (только анимация; состояние «открыто» не сохраняется никогда).

- **Прерывание:** закрытие PWA до точки фиксации → загрузка у ворот на перегоне, сцену можно
  начать заново. После фиксации → загрузка на платформе, сцена не повторяется.
- **Повтор:** после `post1ReturnDone` сцена не проигрывается. Можно ли потом проходить через
  Пост 1 (короткая версия без сцены) — решение автора. Сейчас нельзя.
- Со стороны платформы Пост 1 остаётся закрытым всегда (осмотр «закрыто»). Двустороннего
  перехода нет.
- Тоннель к «Московской» не открывается: в данных нет ни одного портала к восточному посту.

## 3. Четыре сюжетных слота и «Архив → Ключевые предметы»

### Контракт данных (на согласование с DeepSeek)

Справочник предметов (в коде, не в сохранении):
```
ITEMS['deda-card'] = { kind: 'story', reusable: true, title: 'Карта Деда', protected: true }
```

Состояние в сохранении — **одна** запись на предмет:
```
story: { 'deda-card': 'slot2' }   // 'slot0'..'slot3' | 'archive' | 'used'; нет ключа — ещё не получен
```

- **Один экземпляр по построению:** у предмета ровно одно поле местоположения, поэтому
  оказаться сразу в архиве и в ячейке он не может.
- **Атомарность:** перемещение — это смена одного значения в одной записи сохранения.
- **Рюкзак не участвует:** сюжетные предметы в рюкзак не кладутся и не зависят от его
  заполненности.
- **Одноразовый предмет** после использования получает `'used'` и уходит из ячеек;
  факт применения хранит квестовый флаг.
- **Владение и запись в архиве различаются однозначно:**
  - `'archive'` — предмет у Глеба, но не в активном наборе (кнопка «Взять», если есть
    свободная ячейка);
  - `'used'` и прочитанные сведения — только запись истории, без кнопки.
  - В интерфейсе это разные строки и разные значки.
- Личный жетон и пропуск Глеба — отдельная постоянная ячейка, вне этих четырёх.

### Гарантия «не больше четырёх»

- Таблица сценария: стадия → какие сюжетные предметы обязаны быть активны.
- Тест: для каждой стадии таких предметов ≤ 4. Тогда сюжет **не может** потребовать пятый.
- При завершении стадии многоразовый предмет, больше не нужный, может уйти в архив
  (автоматически или по действию игрока — решение автора).
- Выдача сюжетного предмета не должна завершаться отказом.

### Вопрос автору: дверь и карта в архиве

Что делать, если Глеб подходит к двери A, а карта лежит в архиве? Предлагаю у двери действие
«Достать карту из архива» (одно нажатие), если есть свободная ячейка.
Без согласования ничего не реализуется.

## 4. Противогаз, ПНВ и абсолютная темнота

### Слоты экипировки

- Пять категорий одежды (§ 6) плюс два отдельных носимых слота: **лицо** (противогаз)
  и **оптика** (ПНВ).
- Совместимость задаётся в справочнике предметов:
  - `fitsGasMask` у головных уборов;
  - `fitsNvg` у шлемов и противогазов.
- Порядок слоёв на спрайте: тело → штаны → ботинки → куртка/броня → перчатки → противогаз →
  головной убор → ПНВ.

### `requiresGasMask` — только где указано

- Свойство портала или участка сцены:
  - `requires: { equip: ['gasmask'] }`;
  - `hazard: { kind: 'gas', x: [x0,x1] }`.
- Без противогаза переход не начинается, у границы участка — мягкая стена и реплика Глеба.
- Урон, ресурс фильтров, скорость загрязнения и время пребывания **не вводятся**: схема
  только оставляет для них место.
- Сюжетное условие — тот же механизм: `requires: { flag: … }`.

### Абсолютная темнота

- Свойство сцены или помещения: `dark: 'absolute'`.
- Заливка карты освещения — `[0,0,0]` независимо от режима яркости. Видно только то, что
  освещают фонарь, лампы NPC и источники в самой сцене.
- **Вопросы автору:**
  - Действует ли режим «Светлее» на абсолютную темноту? Рекомендую нет — иначе исчезает
    смысл локации.
  - Нужен ли Глебу едва заметный контур вне луча, чтобы игрок видел самого героя?
    Рекомендую минимальный контур.

### ПНВ

- Включённый ПНВ заменяет карту освещения равномерным уровнем в пределах **видимой области
  текущего этажа** и окрашивает кадр в палитру ПНВ. Это одна заливка и обработка кадра.
- Видимая область — объединение открытых помещений текущего этажа сцены, по тем же
  прямоугольникам, которыми уже обрезается свет.
  - Закрытые помещения и соседние этажи остаются чёрными → нет «рентгена».
  - Геометрия не меняется.
- Эффект рисуется в мировом буфере, поэтому автоматически правильно работает с камерой
  и всеми масштабами.
- Выключение — обычная карта освещения.
- **Вопросы автору:**
  - цвет палитры;
  - исключает ли ПНВ фонарь (предлагаю: при ПНВ фонарь выключается — иначе засветка);
  - аккумулятор;
  - совместимость с противогазом.
- Для будущего обнаружения врагами хранится признак «Глеб светит / не светит».
  Невидимость не подразумевается.

## 5. Валютные патроны и защищённый Colt (контракт на согласование с DeepSeek)

### Модель

- Деньги — кошелёк `wallet` (валютные патроны).
- Обычные патроны — запас по калибрам `ammo[калибр]`.
- У каждого экземпляра оружия магазин: `mag = { n, cur }` — всего патронов и сколько из них
  валютных. Режим стрельбы оружия: валюта или обычные.

### Правило порога 25 (без обхода через магазин)

- Валютные патроны попадают в магазин **только при перезарядке** и не больше
  `max(0, wallet − 25)`.
- Значит, стрельба не может опустить кошелёк ниже 25, сколько бы магазинов ни было
  заряжено заранее.
- Когда валюту зарядить больше нельзя:
  1. Глеб один раз предупреждает (флаг сбрасывается, когда кошелёк снова > 25).
  2. Режим переключается на обычные патроны.
  3. Если обычных нет, стрельба останавливается.
- Правило действует и при нуле обычных патронов.
- Торговля: в магазине кошелёк можно тратить до 0. Защита касается только стрельбы.
- Если на старте или после покупок кошелёк < 26 — стрелять валютой нельзя.
- Выбрасывание оружия: магазин разряжается обратно (обычные → `ammo`, валютные → `wallet`).
  Ничего не теряется и не дублируется, выгоды от этого нет.

### Автоперезарядка

- Запускается, когда магазин пуст и есть подходящие патроны. Отдельной кнопки нет.
- Изменение магазина и запаса применяется **в конце** анимации одной операцией.
- Если смена оружия прерывает перезарядку, ничего не теряется.

### Счётчик патронов

- В игре — только у экипированного оружия.
- В открытом рюкзаке — у каждого оружия.
- Отдельных ячеек для патронов нет.

### Пустое оружие

- Обычное оружие без патронов можно оставить экипированным, убрать, выбросить, заменить
  холодным.
- Метнуть во врага — **отдельным** действием, только если магазин пуст и предмет
  не защищён. Урон, дальность и возврат предмета не определены.
- Если другого холодного оружия нет, остаётся нож Фина.

### Защищённые предметы

- Colt Python Фина и нож Фина: `protected: true` → нельзя выбросить, метнуть, продать,
  уничтожить.
- Colt можно экипировать пустым.
- При попытке выбросить — реплика Глеба о памяти отца, текст утверждает автор.
- Colt выдаёт Нефёдов по сюжету. Будущее узнавание по Colt — свойство предмета для сценария,
  не готовая сцена.

## 6. Сменная одежда и визуальные слои

### Игровой спрайт

Генератор уже строит спрайты из палитры и опций, поэтому одежда ложится на него естественно:
- предмет одежды = `{ slot, palette: {jacket, jacketHi, jacketSh, …}, shape: 'cap'|'ushanka'|'helmet'|'vest'|'heavy'… }`;
- палитра героя = базовая + палитры надетых вещей;
- форма — несколько вариантов силуэта на категорию, их рисует код.

| Категория | Варианты силуэта (пример, на утверждение) |
|---|---|
| Шапка / головной убор | нет · шапка · ушанка · каска / шлем |
| Куртка / корпус | лёгкая · плотная куртка · жилет · тяжёлая броня |
| Перчатки | нет · перчатки · тактические |
| Штаны | обычные · усиленные |
| Ботинки | обычные · тяжёлые |

- Комплект кадров героя (≈18 холстов 26×42) перестраивается **один раз** при смене одежды
  и кешируется по набору вещей. Это миллисекунды; тысячи заранее нарисованных сочетаний
  не нужны.
- Путь от одежды к тяжёлой броне — последовательность предметов с силуэтом и палитрой.
  Классы защиты не вводятся.

### КПК

- У модели героя своё, более высокое разрешение.
- Рекомендация — **послойная кукла**: база + отдельный слой каждой вещи на общей «стойке»,
  по эталону KPK_MASTER_APPROVED_2026-10-31.png.
- Заранее собранные комбинации — запасной вариант, только для КПК и только если слои
  смотрятся плохо.

| Где рисуется | в мировом буфере, как сейчас | отдельным проходом в экранном разрешении поверх увеличенного кадра |

| Масштабы 100–175 % | целые ×4–×7, без дрожания | у исходника ×2 шаги ×2 / ×2,5 / ×3 / ×3,5: на 125 % и 175 % дробная выборка, дрожание пикселей; чисто только у исходника ×4 и больше |
| Стиль | един с окружением | разные размеры пикселей у героев и мира («миксели») |
| Одежда и NPC (§ 6, § 8) | дешёвая генерация из палитр | вчетверо больше рисования на каждый вариант |
| Объём работ | малый | крупный этап рендера и риск регрессий |

- Тест: статичная сцена (свет, темнота, арка, фонарь) с героем и двумя NPC в обоих вариантах,
  на iPhone при 100 / 125 / 150 / 175 %.
- Решает автор. Технически рекомендую **А**, если тест не покажет явного выигрыша Б.
- До теста разрешение спрайтов не меняется.

## 8. Стандарт восьми типовых NPC

### Архетип

```
{ archetype: 'resident-m'|'resident-f'|'elder'|'young'|'tech'|'guard'|'trader'|'stalker',
  palettes:[…варианты], shapes:{hat:[…], jacket:[…], …}, behaviors:[…], lamps:[…] }
```

### Экземпляр

```
{ id, archetype, seed, … }
```

- Внешность выбирается из вариантов архетипа детерминированно по `seed`. NPC выглядит
  одинаково при каждой загрузке, и в сохранение это не пишется.
- Тот же генератор и та же система одежды, что у Глеба (§ 6), — один код на всех.
- Поведение — из уже существующих: ходьба по маршруту, стоит, сидит, лежит, пост охраны
  с лучом. Новые пресеты:
  - «работа у агрегата» (техник);
  - «за прилавком» (торговец);
  - «уходит и возвращается через шлюз» (сталкер, позже).
- Нынешние наборы распределяются по архетипам: `guard` → охранник, `worker`/`worker2` → техник,
  `medic` и `resA–C` → жители.
- **Сюжетные NPC** (Нефёдов, Дед, молодой продавец) — отдельные уникальные описания
  с фиксированным `id`, не из пула.
- Память: 8 архетипов × ~4 варианта × ~14 малых кадров — порядка 2 МБ, для iPhone допустимо.

## 9. Сохранения, миграции, выпуск PROD/DEV

### Один источник истины

- Предлагаю **одну корневую запись игры** `pv.game.v2` (DEV — `pv.dev.game.v2`). Разделы:
  - `scene` и позиция;
  - `quest` (стадия и флаги);
  - `story` (4 ячейки и архив);
  - `inventory` (схема inv_v3 от DeepSeek);
  - `equip` (одежда, противогаз, ПНВ);
  - `weapons` (магазины, режимы);
  - `wallet` и `ammo`.
- Схемы inv_v3 / quest_v3 становятся **разделами** этой записи, а не отдельными ключами.
  Тогда конкурирующих источников нет.
- Почему одна запись: `localStorage.setItem` атомарен для одного ключа. Позиция, флаги
  и предметы, которые должны меняться вместе (переход, выдача карты, событие Поста 1,
  покупка), пишутся **одной** операцией. Расхождения между ключами исключены.
- Отдельными остаются настройки и мир, они не меняются: `pv.power.v1`, `pv.scavenge.v1`,
  `pv.visual.v1`, `pv.zoom.v1`.
- Запись происходит в точках фиксации (переход, выдача или перемещение предмета, дверь,
  покупка, конец перезарядки) и при `pagehide`.

### Миграция

- При первой загрузке новой версии `pv.player.v1` превращается в `pv.game.v2`
  (`scene: 'station'`, остальное по умолчанию).
- Ключ `v1` **не удаляется**, поэтому откат на 1.1.0 продолжает работать.
- У записи есть версия `v` и цепочка мигрирующих функций.
- Каждый раздел проверяется отдельно: повреждённый инвентарь сбрасывается к безопасному
  значению, а позицию и флаги не трогает.
- Невозможная позиция → безопасная точка входа этой сцены.

### Выпуск

1. Вся работа — только в `dev`; сохранения DEV и PROD изолированы, как сейчас.
2. Ветка `release/x.y` от **принятого** коммита `dev`. В ней только релизные правки: версия,
   кэш service worker, документы, архив прошлой версии.
3. PR → тесты → приёмка автора на iPhone → слияние → тег (создаёт автор вручную).
4. Обязательные тесты обновления: сохранение PROD 1.1.0 → новая версия
   (позиция, энергия, лут, масштаб не потеряны).
5. Никакого отката `dev` к `main` с потерей работ. Никакого прямого переноса непроверенного
   `dev` в PROD.
6. После выпуска обновить статусы и SHA в документах обеих веток.

## 10. Риски, тесты, порядок коммитов

### Риски

1. **Слой сцен** — крупнейший рефакторинг. Делать отдельно, без видимых изменений,
   с полной регрессией.
2. **Корневая запись сохранений** — ошибка миграции бьёт по всем игрокам. Нужны тесты
   обновления и сохранение старых ключей.
3. **Изменения рендера** (абсолютная темнота, ПНВ, при варианте Б — персонажи) трогают самый
   чувствительный код: свет, вырезы свечения, арки.
4. **Расширение генератора спрайтов** под одежду — риск изменить нынешний вид Глеба
   и NPC. Нужен снимок «до/после» по пикселям.
5. **Экономика патронов** — обходы порога. Нужны тесты на случайных последовательностях.
6. **Производительность iPhone** — загрузка сцен по требованию, ограничение кешей.
7. **Объём** — много систем сразу. Строго по одной системе на этап.

### Тесты

- Валидаторы данных:
  - непересечение участков и полных зон разговора;
  - ≤ 4 активных сюжетных предмета на каждой стадии;
  - уникальность предметов;
  - у гермоворот нет условия «карта»;
  - нет портала к «Московской».
- Граф порталов: из любой сцены, при любом наборе флагов, есть путь домой.
  Пост 1 со стороны станции не открывается (правила I1–I8 из ST-002_PLAN).
- Патроны: тысячи случайных последовательностей «зарядить / выстрелить / купить / выбросить /
  сменить оружие» — стрельба ни разу не опускает кошелёк ниже 25, сумма патронов сохраняется.
- e2e в репозитории (Playwright, сейчас эти тесты лежат вне репо):
  - переходы;
  - закрытие PWA в середине анимации;
  - перезагрузка после точки фиксации;
  - снимки на 4 масштабах.
